# Compliance Control Mappings

Aegis maps its findings to compliance-framework controls so a scan doubles as
**technical evidence** for an audit. The mapping pivots on two stable properties
every finding carries — its **CWE** (`cwe_id`) and **OWASP** category
(`owasp_category`) — plus the scanner **pillar** (security / deployment).

## How the mapping works

Each framework file (`frameworks/<framework>.yaml`) lists the controls Aegis can
provide evidence for. A control declares the finding signals that map to it:

```yaml
- id: CC6.1
  name: Logical & Physical Access Controls
  evidence:
    owasp: ["A01:2021", "A07:2021"]     # OWASP Top-10 2021 categories
    cwe:   ["CWE-284", "CWE-287"]        # CWE identifiers
    pillars: ["security"]
```

At report time each finding is attributed to **exactly one** control (J1). Evidence
keys are mutually exclusive across controls, and where a finding's CWE and its
OWASP category still point at different controls a precedence rule decides: a
finding carrying a CVE is attributed by OWASP category (a dependency CVE is
evidence about vulnerability management, and its CWE describes a third party's
bug, not the customer's code); otherwise the CWE wins as the more specific
statement. Attributing to *every* matching control inflated both the evidence and
the failure count — 9,871 double-attributions across a 14,041-finding corpus.

A control with ≥1 open (non-suppressed, non-false-positive) finding is
**Needs attention**. A control with none reads **"no findings"** — deliberately not
"passing", because it means this scan produced no failing evidence, not that the
control was tested and operates effectively.

Three scope states exist:

| `aegis_scope` | meaning | counted in the score? |
|---|---|:--:|
| *(absent)* | assessed — we have a detector that can fail it | yes |
| `not-assessed` | real control, but static analysis cannot evidence it either way (runtime monitoring, change approval, patch installation) | **no** — excluded from both sides |
| `out-of-scope` | organizational, physical or process control | no — "requires external evidence" |

Every evidence identifier must be one an engine can actually emit; the inventory is
`emittable_identifiers.yaml`, regenerated by
`scripts/refresh_emittable_identifiers.py` and enforced in CI by
`tools/check_single_framework_tree.py`. A mapping to an identifier nothing emits
would make a control read "no findings" when the truth is "never checked" — J2
removed 36 such entries.

## Honest scope

Aegis performs **static application + dependency + secret + IaC analysis**. It
can therefore evidence the *technical / code-level* controls of a framework —
injection defenses, crypto usage, access-control patterns in code, dependency
CVEs, secret hygiene, deployment misconfig. It **cannot** attest to
organizational, physical, HR, or process controls (background checks, physical
security, vendor management, incident-response drills). Those are marked
`aegis_scope: out-of-scope` and appear in reports as *"requires external
evidence"* — never as passing.

Each framework file also declares its **scope** — how large the standard is, how
much of it a static scanner can reach, and whether the control text was verified
against the published normative document or only against published numbering and
titles. Only **OWASP ASVS** and **SOC 2** are headline claims; the rest print
"SUPPORTING EVIDENCE ONLY" on the generated report itself.

**These mappings are a reviewed, defensible starting point, not a certification.**
A qualified auditor/assessor must validate scope and evidence before any formal
attestation. Every generated report carries this disclaimer.

## Frameworks

| File | Framework | Basis |
| --- | --- | --- |
| `frameworks/soc2.yaml` | SOC 2 | 2017 Trust Services Criteria |
| `frameworks/pci_dss.yaml` | PCI-DSS 4.0 | Requirements 2, 3, 4, 6, 8 |
| `frameworks/hipaa.yaml` | HIPAA Security Rule | §164.312 Technical Safeguards |
| `frameworks/iso27001.yaml` | ISO/IEC 27001:2022 | Annex A (8.x technical) |
| `frameworks/owasp_asvs.yaml` | OWASP ASVS 4.0 | L1/L2/L3 verification reqs |
| `frameworks/nist_csf.yaml` | NIST CSF 2.0 | Function/Category/Subcategory |

This directory is the **single source** for the mappings — `report.py` resolves
them relative to its own location, and they ship inside the scanner image. A second
copy once existed at the repository root and diverged silently through an entire
correction pass; CI now fails if one reappears.
