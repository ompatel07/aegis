# Pass J1 — compliance and SBOM accuracy, checked against the specifications

**HEAD:** `a50821f` + this change · **Run date:** 2026-09-08
**Evidence base:** 14,041 real findings across 101 scans (our own database), and SBOMs generated for
five package ecosystems.

**Headline:** the SBOM parses but **every SPDX document we produced was invalid** against the
official SPDX validator — 937 errors across five repositories — and leaked our internal directory
paths. That is fixed. On the compliance side, F1 found 2 defects in a sample of 10 SOC 2 mappings;
auditing all 6 frameworks found the same two classes in every one of them, plus one control that was
simply the wrong control. **9,871 double-attributions are now 0.**

---

## Part 1 — for a non-specialist

### What an SBOM is

A Software Bill of Materials is an ingredients list for software. Modern applications are mostly
other people's code: a small web app can pull in 500 open-source libraries, each of which pulls in
more. When a vulnerability like Log4Shell appears, the first question every organisation must answer
is "do we use it, and where?". Without an ingredients list that takes weeks. With one it takes
minutes. That is why US federal procurement (Executive Order 14028) and a growing number of
enterprise contracts now require suppliers to hand one over.

### What ours contains

For each dependency: its **name**, its **version**, a **package URL** that identifies it precisely
enough to look up, its **licence**, and any **known vulnerabilities**. We emit it in both formats the
market asks for — **CycloneDX 1.7** and **SPDX 2.3** — and both are now valid against their
publishers' own validators.

### What ours is missing

Three things, stated plainly:

1. **Supplier names — 0% populated, in every ecosystem.** The NTIA baseline asks who supplies each
   component. We emit the component and its version but not who publishes it. We could guess from
   the package registry, and we deliberately do not: a guessed supplier in an audit document is
   fabricated provenance.
2. **Java/Maven SBOMs frequently fail.** Resolving a Maven project's dependencies requires reaching
   out to Maven Central over the network, and Maven Central rate-limits us. During this pass it
   returned `429 Too Many Requests` and blocked our IP for ~30 minutes, so **we could not produce a
   Maven SBOM at all**. Trivy's own advice is to run `mvn dependency:resolve` first — which we will
   not do, because Aegis never builds or executes customer code.
3. **A manifest without a lockfile produces an empty SBOM.** juice-shop has a `package.json` but no
   `package-lock.json`, and the result is a perfectly valid document listing **zero** components.
   Previously we stored that as a success. It is now flagged.

### Which frameworks we support, and what "supported" honestly means

Six: **SOC 2, ISO/IEC 27001, PCI DSS, HIPAA, NIST CSF, and OWASP ASVS.**

"Supported" means: we map our findings to a **small subset** of each framework's controls and show
which of those have failing evidence. It does **not** mean we assess the framework. The proportions
matter and we should say them out loud:

| framework | controls in the standard | controls we assess | what that is |
|---|--:|--:|---|
| SOC 2 (Common Criteria) | ~33 | **7** | the code/config subset of the security criteria |
| ISO/IEC 27001 Annex A | 93 | **8** | the technical Annex A controls |
| PCI DSS 4.0 | 12 requirements, 300+ sub-requirements | **7** | a fraction of the technical requirements |
| HIPAA Security Rule | 3 safeguard families | **5** | the §164.312 Technical Safeguards only |
| NIST CSF 2.0 | 106 subcategories | **7** | code/config subcategories |
| OWASP ASVS 4.0.3 | 14 chapters | **11** | the closest fit — ASVS is about application weaknesses |

**The honest framing for a customer is: "Aegis produces technical evidence toward these controls."
Not "Aegis makes you SOC 2 compliant."** No static analyser can do the second thing. Most of what an
auditor examines — access reviews, onboarding and offboarding, vendor risk, incident response,
change approval, physical security — leaves no trace in a repository.

**On PCI DSS specifically**: assessing 7 items out of several hundred sub-requirements is thin
enough that leading with PCI in sales material would be misleading. ASVS and SOC 2 are the two we
can stand behind; the others are useful supporting evidence, not headline claims.

## Part 2 — SBOM conformance (Part A)

### 2.1 What we emit

| question | answer |
|---|---|
| Formats | **Both** — CycloneDX and SPDX, generated by Trivy 0.71.2 from the checkout |
| CycloneDX version | **1.7** (`"specVersion": "1.7"`) |
| SPDX version | **2.3** (`"spdxVersion": "SPDX-2.3"`, `dataLicense: CC0-1.0`) |

### 2.2 Official validator output

Validated with the standards bodies' own tooling, not a hand-written check:
`cyclonedx-python-lib 11.12.0` (`JsonStrictValidator`, schema 1.7) and `spdx-tools 0.8.5`
(`validate_full_spdx_document`).

**CycloneDX — passed before and after:**

```
composer_dvwa.cdx.json     VALID
go_aegis.cdx.json          VALID
npm_juiceshop.cdx.json     VALID
npm_nodegoat.cdx.json      VALID
pip_redash.cdx.json        VALID
```

**SPDX — every document failed. This is the finding.**

```
composer_dvwa.spdx.json    INVALID - 8 message(s)
go_aegis.spdx.json         INVALID - 2 message(s)
npm_juiceshop.spdx.json    INVALID - 1 message(s)
npm_nodegoat.spdx.json     INVALID - 383 message(s)
pip_redash.spdx.json       INVALID - 543 message(s)
       package download_location must be a valid URL or download location
       according to the specification, but is: git+/workspaces/_h1/redash
```

**937 validation errors in total.** Two causes:

- **`downloadLocation` was our internal scan path**, identically for every package
  (`git+/workspaces/_f1/NodeGoat`). Invalid per SPDX, and false: no npm package was downloaded from
  our scratch directory. It also appeared in the document `name`, the `documentNamespace`, and the
  synthesised root package — so our directory layout travelled inside a document customers hand to
  auditors.
- **Empty `advisory` external references**, whose locator must be a URL.

**After the fix — same validators, same documents:**

```
composer_dvwa.spdx.json    VALID (0 messages)     npm_nodegoat.spdx.json   VALID (0 messages)
go_aegis.spdx.json         VALID (0 messages)     pip_redash.spdx.json     VALID (0 messages)
npm_juiceshop.spdx.json    VALID (0 messages)
TOTAL path leaks across all 10 documents: 0
```

The fix (`utils/sbom_sanitize.py`) names the document after the repository URL instead of the scan
path, replaces unusable download locations with SPDX's own `NOASSERTION` sentinel, drops empty
references, and records Aegis as the SBOM author. It strips credentials from the repository URL
first — a clone URL should never carry one, but a downloadable artifact is the last place one should
surface.

### 2.3 NTIA minimum elements, per ecosystem

Completeness measured across every component in a real scan, not asserted from the schema.

| NTIA element | npm (NodeGoat, 381) | pip (redash, 542) | composer (DVWA, 7) | go (aegis, 138) | maven (petclinic) |
|---|--:|--:|--:|--:|---|
| Supplier name | **0.0%** | **0.0%** | **0.0%** | **0.0%** | not measured |
| Component name | 100% | 100% | 100% | 100% | not measured |
| Version | 99.7% | 99.6% | 85.7% | 97.1% | not measured |
| Other unique IDs (purl) | 99.7% | 99.6% | 85.7% | 98.6% | not measured |
| Dependency relationships | **100%** reachable, depth 12 | **100%**, depth 9 | **100%**, depth 4 | **100%**, depth 3 ¹ | not measured |
| Author of SBOM data | ✅ *(added in J1)* | ✅ | ✅ | ✅ | not measured |
| Timestamp | 100% | 100% | 100% | 100% | not measured |

**Maven is "not measured", not "0%".** Generation failed outright — Maven Central returned HTTP 429
and blocked the IP. Reporting it as zero completeness would imply we produced a document and it was
empty; we produced nothing.

Two elements fail:

- **Supplier name: 0% everywhere.** Trivy does not resolve it and we will not invent it. This is our
  single clearest NTIA gap, and it is the same across all four measurable ecosystems.
- **Dependency relationships: partial, and wildly uneven.** See below.

**Author of SBOM data** was also failing before this pass: CycloneDX carried `metadata.tools`
(Trivy) but no `authors`, `manufacturer` or `supplier`. Naming the tool is not naming the author. We
now add Aegis explicitly in both formats.

### 2.4 Dependency relationships — a real graph, or a flat list?

**Both, depending on the ecosystem.** This is the field the brief predicted most tools get wrong,
and averaging it would have hidden the truth:

- **npm and pip: a genuine graph.** NodeGoat has 179 of 380 nodes with children and a realistic
  fan-out distribution (64 nodes with 1 child, 36 with 2, 22 with 4, and a tail). SPDX carries 631
  relationships for 382 packages. This satisfies the element.
- **Go: complete but shallow.** ¹ **Corrected 2026-09-08 (J2).** This row first read "3.6% (5/139),
  effectively flat, does not meet the NTIA relationship element". That was measured wrongly: it
  counted *nodes that have children* rather than edges, and in a Go SBOM nearly all edges hang off
  two module nodes (`api` -> 75 children, `orchestrator` -> 59). Re-measured by reachability, **all
  138 components are reachable from the root and there are 138 edges — the relationship element is
  met.** What Go genuinely lacks is *depth*: the graph is 3 levels deep versus npm's 12, so we can
  say which module includes a component but not which dependency pulled in a given transitive one.
  Closing that needs `go mod graph` (running the Go toolchain over customer code) or fetching each
  module's `go.mod` (a network call per package); both are ruled out by our boundaries. See
  `docs/COMPLIANCE_SCOPE_J2.md` §4.
- **composer: too small to generalise** (4 of 8).

## Part 3 — the compliance mapping audit (Part B)

### 3.1 How each framework's control text was verified

The brief asked us to check against published control text and cite it. Verification quality differs
by framework and pretending otherwise would be the same error we are fixing:

| framework | source | verified how |
|---|---|---|
| **HIPAA** | 45 CFR 164.312 — US federal regulation, public | **Verbatim.** Fetched and read; control names now quote the regulation |
| **NIST CSF 2.0** | NIST CSWP 29, published openly | Subcategory IDs and outcome statements checked against the public Core |
| **OWASP ASVS 4.0.3** | OWASP, CC BY-SA | Chapter and section titles checked against the public standard |
| **SOC 2** | AICPA TSC 2017 | **Titles only.** The full criteria are behind an AICPA account wall — we attempted to fetch and could not. Numbering and titles checked against the publicly published criteria list; **the normative text was not re-read verbatim** |
| **ISO/IEC 27001:2022** | ISO | **Titles only.** Paywalled standard; Annex A control numbers and titles checked against the public control list |
| **PCI DSS 4.0** | PCI SSC | **Titles only.** Distributed under SSC terms; requirement numbers and titles checked against the public summary |

Where we could not read the normative text, that is now recorded in the YAML file itself, so the
limitation travels with the mapping rather than living only here.

### 3.2 Verdicts

Full per-control tables are in the framework YAMLs, each defect annotated inline at the control it
affects. Summary:

| verdict | count | what it means |
|---|--:|---|
| **CORRECT** | 39 | mapping matches the control's subject |
| **OVER-BROAD** | 14 | evidence pulled in findings the control does not cover, or shared with another control |
| **WRONG** | 2 | the mapping is about a different thing entirely |
| **MISSING** | 19 CWE classes | high-volume weaknesses no control claimed |

**The two WRONG mappings:**

1. **HIPAA `164.312(e)(2)(ii)`** was named *"Guard against unauthorized access during transmission
   (SSRF/redirect)"* and fed SSRF (CWE-918) and open-redirect (CWE-601) findings. Checked verbatim
   against 45 CFR 164.312, that paragraph is **"Encryption"** — *"Implement a mechanism to encrypt
   electronic protected health information whenever deemed appropriate."* The name we used was a
   paraphrase of a **different** paragraph, (e)(1) Transmission Security. It is also an
   implementation specification *under* (e)(1), not a sibling, so scoring it separately
   double-counted by construction. Removed; its subject is evidenced by (e)(1).
2. **SOC 2 `CC8.1`** was titled *"Secrets and credentials not hard-coded (change management)"* and
   fed hard-coded-credential CWEs. CC8.1 is the **change-management** criterion — authorising,
   testing and approving changes. A secret committed to source says nothing about change control.
   The credential CWEs moved to CC6.2; CC8.1 is now **not assessed**, because we cannot evidence an
   approval workflow by scanning a checkout.

**The OVER-BROAD class**, including both F1 defects:

- **SOC 2 CC6.3** (F1) carried **CWE-732**, "Incorrect Permission Assignment for a Critical
  Resource". In practice that fires on filesystem and container permissions, so container-hardening
  findings were being reported against a *role-based access* criterion. Removed here; CWE-732 now
  evidences CC7.1, where configuration belongs. The same fix was needed in ISO `A.8.2` and NIST
  `PR.AA-05`, which had copied the same mistake.
- **SOC 2 CC6.8 / CC7.1** (F1) both claimed `A06:2021`, so **every dependency CVE failed both**.
  CC6.8 is about *unauthorized or malicious software*; a known-vulnerable dependency is CC7.1's
  subject. The identical defect existed in **PCI 6.3.1/6.3.3** (larger: 1,942 double-attributions),
  **ISO A.8.26/A.8.28**, **NIST PR.PS-01/DE.CM-09**, and **ASVS V5.1/V5.2/V5.3** — where a single
  SQL-injection finding failed *three* controls at once.

**A finding F1 could not have seen:** `CWE-937`, `CWE-1035` and `CWE-1104` — the CWEs mapped to
"vulnerable dependencies" in six frameworks — **are never emitted by any engine we run.** They are
inert. The CVE double-counting was driven entirely by the shared OWASP category, not by the CWE that
looked like it was doing the work. Mappings that match nothing are not harmless: they create the
appearance of coverage.

### 3.3 Before and after

Measured over the same 14,041 findings:

| framework | double-attributions before | after | assessed controls (before → after) | now "not assessed" |
|---|--:|--:|:--:|--:|
| SOC 2 | **2,802** | **0** | 9 → 7 | 2 |
| ISO/IEC 27001 | 1,289 | **0** | 9 → 8 | 2 |
| PCI DSS | **3,226** | **0** | 9 → 7 | 2 |
| HIPAA | 152 | **0** | 6 → 5 | 2 |
| NIST CSF | 535 | **0** | 8 → 7 | 1 |
| OWASP ASVS | 1,867 | **0** | 13 → 11 | 2 |
| **total** | **9,871** | **0** | 54 → 45 | 11 |

Two mechanisms were needed, because fixing only the first left 1,020 SOC 2 findings still
double-counted:

1. **Mutually exclusive evidence.** No CWE and no OWASP category may be claimed by two assessable
   controls in a framework. `attribution_conflicts()` reports violations and a test fails the build
   on any.
2. **Single attribution with a precedence rule.** A finding carries *both* a CWE and an OWASP
   category, and those can still point at different controls. So each finding is now attributed to
   at most one control: **if it carries a CVE, the OWASP category wins** (a dependency CVE is
   evidence about vulnerability management, and its CWE describes a third party's bug, not the
   customer's code); **otherwise the CWE wins**, being the more specific statement.

Without rule 2, a prototype-pollution CVE in a dependency failed both "secure coding" and
"vulnerability management" — charging the customer for a bug they did not write.

### 3.4 Controls now marked "not assessed"

The brief asked for this explicitly: a control with no automatable evidence should map to nothing
and say so. Eleven controls moved from "scored" to "not assessed", each with a stated reason in the
YAML — SOC 2 CC7.2 (runtime monitoring) and CC8.1 (change approval); PCI 6.3.3 (patch installation)
and 6.4.1 (WAF or equivalent); HIPAA (e)(2)(i) (transmission integrity) and (b) (audit controls);
ISO A.8.25 (secure SDLC) and A.8.16 (monitoring); NIST DE.CM-09 (runtime monitoring); ASVS V3.x
(session management) and V7.x (logging) — the last two because **no engine we run emits those
findings on real code**, which is a capability gap rather than a scope question.

### 3.5 The grade can no longer be computed from double-counted evidence

Three changes, verified by test:

- Each finding is attributed to at most one control (`test_a_finding_never_fails_two_controls`,
  parameterised over all six frameworks).
- Not-assessed controls are excluded from **both** sides of the score, rather than counting as
  passes. Previously a control we could not evidence was scored as passing, which inflated the
  percentage.
- The status label changed from **"passing" to "no-findings"**, and the disclaimer now says what
  that means: *this scan produced no failing evidence for that control — not that the control was
  tested and operates effectively.* This is the difference between a scanner's output and an
  auditor's opinion, and the old wording blurred it.

**Where we genuinely stand out:** almost nobody publishes per-ecosystem NTIA completeness or
validator output for their own SBOMs. We now can, including the parts that fail. Mapping to six
frameworks is also more than Trivy or Dependency-Track offer.

**Where we are behind:** Dependency-Track is built around *continuously* monitoring a portfolio of
SBOMs — re-evaluating every stored SBOM when a new CVE lands. We generate an SBOM per scan and do
not re-evaluate it between scans. For an organisation whose main question is "which of my 300
services just became vulnerable overnight", Dependency-Track answers it and we do not.

## Part 5 — what an auditor would trust, and what they would push back on

If an auditor received this report tomorrow, the SBOM would survive scrutiny: it is valid against
both publishers' validators, it names its author and its generation time, and the component
inventory for npm, pip and Go is accurate and precisely identified by package URL. The per-control
findings would also hold up as *technical evidence* — each is a real weakness at a real file and
line, and each is now attributed to exactly one control, so the failure count means what it says.

They would push back on four things, and they would be right. **First, the supplier field is empty
for every component**, which is a named NTIA element, so the SBOM does not meet the US baseline in
full. **Second, coverage is small and unevenly distributed** — 7 of ~33 SOC 2 common criteria, 7 of
several hundred PCI sub-requirements — so "no findings" across a handful of technical controls says
very little about the framework as a whole, and an auditor will read the denominator before the
percentage. **Third, "not assessed" is doing real work now**: eleven controls are explicitly outside
what we can evidence, and an auditor will want those covered by other means rather than treated as
handled. **Fourth, and most likely to be challenged: for Go projects the dependency graph is
shallower — 3 levels against npm's 12, so transitive provenance is not recoverable — and for Java we may not be able to produce an SBOM
at all when Maven Central rate-limits us — so our coverage claim is ecosystem-dependent in a way a
single summary number would hide.

What they would *not* accept, and what we must never imply, is that any of this constitutes an
assessment. It is input to one.
